fix(worker): concurrency + freshness window; relax over-literal test

Three real problems surfaced by running the suite, all fixed:

1. test_08 flagged the literal token `hiring_signals` because it appeared in the
   docstring explaining what had been removed. The string itself was already
   gone from the field definitions; rephrased the comment so the assertion stays
   strict. test_08 now passes.

2. Throughput: the worker executed runs strictly one at a time, so a backlog
   serialised and later requests timed out waiting behind earlier ones. Runs are
   I/O-bound (search + scrape + LLM + Places), so the worker now uses a small
   thread pool (SYNDICATE_WORKER_CONCURRENCY, default 3) via process_task().

3. The queue never drained. Completion is published as a NEW row
   (status done:<id>) rather than updating the original, so every original
   pending row stayed pending forever and each worker restart re-ran the entire
   historical backlog (14 stale rows on this run alone). Added a freshness window
   (SYNDICATE_PENDING_MAX_AGE_S, default 1800s) so only recent requests are
   claimed. A true fix needs an update route, which Helix does not currently
   serve for this table.

Also raised the suite's research timeouts to 480s. A run legitimately takes
1-4 minutes because the Python Anakin client spawns a fresh `npx` MCP subprocess
per tool call (~7 per run); the previous 200-280s timeouts were sized for the old
instant path. The underlying inefficiency is recorded in PLAN open items.
